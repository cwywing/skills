# Phase 3：文档鉴别材料生成细则

读完本文件后，打开 `assets/document_prompt.md` 作为结构清单执行。  
**脱敏**：写作与交付遵守 `references/content-redaction.md`。

---

## 输入

- `md素材/codebase_data.json`（Phase 1）
- `assets/document_prompt.md`（章节与格式）
- `基础资料.md` 中的文字描述（与 JSON `software_info` 冲突时以基础资料为准）
- 项目业务文档（如有 `.ai/domain.md`）仅作事实来源，写入说明书时去单位名与绝对路径

---

## 结构硬规则（不可颠倒）

说明书必须按 **「背景 → 蓝图串联 → 流程详解 → 模块索引」** 组织。  
**禁止**一上来按 Controller/模块堆砌，让读者自己拼链路。

| 顺序 | 内容 | 要求 |
|------|------|------|
| 0 | 首页说明（强制） | 在正文前增加 `## 说明`：简述材料用途；并固定三行 **`权利人署名` / `软件名称` / `软件版本号`**（取值与 `基础资料.md` 申请表一致） |
| 1 | 软件概述 | 全称/版本/用途；正文其余章节**默认不重复**著作权人单位全称 |
| 2 | 项目背景 | 写厚：行业语境、建设前痛点、建设目标、范围边界（做什么/不做什么） |
| 3 | 总体业务蓝图 | ASCII/文字主链路 + 角色表 + 3～4 个端到端故事（先连起来） |
| 4 | 系统总体设计 | 架构定位、与外部系统职责对照、技术约定 |
| 5 | 按流程详解（主文） | 每条流程固定：**触发 → 步骤 → 关键规则 → 结果/异常**；写具体 |
| 6 | 功能模块对照（后置） | 模块可拆，但必须标明「对应哪条流程」；短写，不重复讲流程 |
| 7 | 数据 / 环境 / 界面 / 使用 / 特色 | 支撑章节 |

流程集合从真实代码归纳；集成类项目至少覆盖主数据同步、核心单据流转、通知、回写/闭环；若有工时、巡检、审批、文件产出等，**应单列流程**，不要只塞进模块列表。

---

## 写作原则

1. **忠于代码**：模块、表名、路由、方法名来自 JSON；禁止编造未出现的支付/商城/直播等。
2. **先故事后零件**：蓝图与流程章以业务语言为主，少堆类名；模块章再给代码索引。
3. **充分展开**：每章写成可打印说明文，避免「一句话标题 + 空列表」。
4. **可分段**：`-1`～`-4`（最多 `-6`）。
5. **无敏感信息**：见 `content-redaction.md`（路径、单位名、密钥、邮箱、生产 URL）。

---

## 篇幅校准

- 目标：合并转 Word/PDF 后 **≥ 60 页**（可按完整性适当超出，建议约 60～80）。
- 宜多用 **流程图 / 时序图 / 状态图 / ER 图 / 界面布局示意**（ASCII 即可）增加可读性与页数；禁止虚构模块与无意义注水。
- 背景与流程章写够；库表多时加长数据章；**禁止**用重复空话灌水同一段。
- **MD 行数 ≠ PDF 页数**（表格/图例多时更不可用「行数÷30」拍脑袋）。写完必须跑 Phase 4 export；实测不足 60 再补流程细则、字段表、状态机、配置字典或新增 `-5`～`-7`，然后重导。
